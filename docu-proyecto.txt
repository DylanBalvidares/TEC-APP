 1. RESUMEN GENERAL
================================================================================

"tec-app-gestion" es un sistema de gestión escolar completo para una escuela
técnica, construido con una arquitectura de microservicios en Node.js.

La aplicación se divide en 6 microservicios independientes más una base de
datos MySQL compartida, todos orquestados con Docker Compose y comunicados a
través de un API Gateway central que actúa como único punto de entrada.

Módulos funcionales:
  - Autenticación y registro (login con JWT + verificación por email)
  - Gestión de usuarios, roles y permisos (RBAC)
  - Gestión académica (alumnos, cursos, profesores, materias, asignaciones,
    notas, asistencias, personal y cargos)
  - Biblioteca (bibliotecas, recursos y préstamos)
  - Comunidad (noticias con imágenes, comunicados por destinatario,
    objetos perdidos)

 5. BASE DE DATOS (gestion_tecnica2)
================================================================================

Base de datos única compartida por TODOS los microservicios.
MySQL 8.0, charset utf8mb4, collation utf8mb4_general_ci.
El esquema completo está en db/gestion_tecnica2.sql.

Conexión (db/conexionDB.js): parsea la variable DATABASE_URL
(ej.: mysql://usuario:clave@host:3306/gestion_tecnica2) y crea el pool de
Sequelize con:
  - charset/collation utf8mb4 (y "SET NAMES utf8mb4 COLLATE utf8mb4_unicode_ci"
    en cada conexión para evitar problemas de tildes/emojis)
  - pool: max 10 conexiones
  - timestamps desactivados globalmente (define.timestamps = false)
  - reintento automático de conexión cada 5 segundos si falla

 6. AUTENTICACIÓN Y AUTORIZACIÓN (RBAC)
================================================================================

El sistema usa RBAC (Role-Based Access Control) con 3 tablas:
roles, permisos y rol_permisos.

Roles definidos (id_rol):
  1 alumno | 2 delegado | 3 profesor | 4 preceptor | 5 bibliotecario |
  6 tutor | 7 administrativo | 8 root

Permisos principales por rol (resumen):

  ALUMNO:        alumno_ver_perfil, alumno_ver_horario, alumno_ver_mis_notas,
                 alumno_ver_mis_asistencias, alumno_ver_mi_curso
  DELEGADO:      hereda alumno + delegado_crear_noticia,
                 delegado_editar_mis_noticias, delegado_eliminar_mis_noticias
  PROFESOR:      profesor_ver_curso, profesor_ver_alumnos_de_curso,
                 profesor_ver_perfil_alumno, profesor_ver_todos_notas,
                 profesor_crear_nota, profesor_editar_nota,
                 profesor_eliminar_nota, profesor_gestionar_asistencias,
                 profesor_ver_horario
  PRECEPTOR:     preceptor_ver_curso, preceptor_ver_alumnos_de_curso,
                 preceptor_ver_perfil_alumno, preceptor_registrar_asistencias,
                 preceptor_ver_asistencias, preceptor_gestionar_sanciones,
                 preceptor_ver_sanciones
  BIBLIOTECARIO: biblio_ver_recursos, biblio_crear_recurso, biblio_editar_recurso,
                 biblio_eliminar_recurso, biblio_gestionar_inventario,
                 biblio_crear_prestamo, biblio_editar_prestamo,
                 biblio_ver_prestamos, biblio_registrar_devolucion
  TUTOR:         tutor_ver_perfil_hijo, tutor_ver_notas_hijo,
                 tutor_ver_asistencias_hijo, tutor_ver_sanciones_hijo,
                 tutor_ver_calendario
  ADMINISTRATIVO: todos los permisos administrativo_* (alumnos, cursos,
                 profesores, asignaciones, materias, usuarios, reportes) +
                 comunicado_crear/editar/eliminar/ver
  ROOT:          TODOS los permisos (incluye root_gestionar_roles,
                 root_gestionar_permisos, root_ver_logs_sistema,
                 root_configurar_sistema, root_eliminar_cualquier_contenido)

Cómo se valida en cada capa:

  1) API GATEWAY (gateway.js):
     - Verifica el JWT (función verificarToken) en todas las rutas EXCEPTO
       /api/auth y /api/comunidad/uploads.
     - Si el token es válido, inyecta en los headers de la petición:
       id_usuario, email e id_rol (tomados del payload del token).
     - Errores: 401 "Token requerido", "Token expirado" o "Token inválido".

  2) SERVICIO-ACADEMICO (middlewares/comprobarPermisos.js):
     - Lee los headers id_rol e id_usuario (inyectados por el gateway).
     - Consulta a http://servicio-usuarios:3310/permisos/:idRol para obtener
       la lista de permisos del rol.
     - Compara si el rol posee al menos uno de los permisos requeridos.
     - Si no: 401 (sin rol/usuario) o 403 (sin permiso).
     - NOTA: cada petición protegida genera una llamada HTTP extra al
       servicio-usuarios.

  3) SERVICIO-COMUNIDAD:
     - Middleware autenticar: verifica el JWT localmente (mismo secreto) y
       guarda el payload en req.user. Aplica a TODAS las rutas.
     - Middleware comprobarPermisos: si req.user.id_rol === 9 permite todo;
       en caso contrario compara req.user.permisos (guardados en el token).
     - Las rutas de creación/edición/eliminación usan comprobarPermisos()
       sin permisos específicos (cualquier usuario autenticado puede crear).

  4) SERVICIO-USUARIOS y SERVICIO-BIBLIOTECA:
     - NO tienen verificación interna de token; se confía en que el gateway
       ya validó. (Solo alcanzables dentro de la red Docker.)

Flujo del token JWT:
  - Payload: { id, nombre, email, id_rol, nombre_rol, permisos }
  - Secreto: JWT_SECRET (default "clave_secreta_super_segura")
  - Expiración: 8 horas (JWT_EXPIRES_IN = "8h")

-----------------------------------------------------------------------------
 7.1 API GATEWAY (puerto 9000) — api-gateway/gateway.js
-----------------------------------------------------------------------------
Propósito: punto de entrada único. Todas las peticiones del frontend pasan
por aquí.

Funciones:
  - verificarToken(req,res,next): extrae el token del header Authorization
    ("Bearer <token>"), lo valida con jwt.verify y agrega los headers
    id_usuario, email e id_rol al request.
  - CORS: configurado para aceptar SOLO el origen
    http://186.0.171.84:7070 (IP y puerto del frontend), con métodos
    GET/POST/PUT/PATCH/DELETE/OPTIONS y credentials.

Rutas de proxy (todas usan createProxyMiddleware):
  - PÚBLICAS (antes de verificarToken):
      /api/auth              → http://servicio-auth:3308        (rewrite quita /api/auth)
      /api/comunidad/uploads → http://servicio-comunidad:3305/uploads
  - PROTEGIDAS (después de verificarToken):
      /api/comunidad  → http://servicio-comunidad:3305  (rewrite quita /api/comunidad)
      /api/academico  → http://servicio-academico:3307  (rewrite quita /api/academico)
      /api/biblioteca → http://servicio-biblioteca:3309 (rewrite quita /api/biblioteca)
      /api/usuarios   → http://servicio-usuarios:3310   (rewrite quita /api/usuarios)

Ejemplo: GET /api/academico/alumnos → servicio-academico recibe GET /alumnos
con headers id_usuario, email, id_rol.

-----------------------------------------------------------------------------
 7.2 SERVICIO-AUTH (puerto 3308) — Autenticación y registro
-----------------------------------------------------------------------------
Responsable del login, registro con verificación por correo y generación
de tokens JWT. Se comunica con servicio-usuarios y servicio-academico.

Rutas (auth-router.js):
  POST /login               → Inicia sesión con {email, contrasena}.
                              Devuelve {token, usuario{..., permisos}}.
  POST /iniciar-registro    → Inicia registro: busca a la persona en el
                              padrón (DNI + fecha de nacimiento), genera un
                              código de 6 dígitos, lo guarda y lo envía por
                              email. Expira a los 15 minutos.
  PATCH /auth/              → Modifica un usuario (reenvía al servicio-usuarios).
  POST /buscar-en-padron    → Busca {dni, nacimiento} en alumnos y profesores.
  POST /verificar-codigo    → Completa el registro: valida el código,
                              crea el usuario, sincroniza el id_usuario con el
                              alumno/profesor correspondiente, invalida el
                              código y devuelve el token.

Controladores:
  - auth-controller.js:
      * generarToken(usuario, permisos): firma el JWT (expira en 8h).
      * login: pide credenciales a servicio-usuarios (/usuarios/login),
        obtiene permisos del rol y genera el token.
      * buscarEnPadron: recorre PADRON_SERVICES (alumnos y profesores del
        servicio-academico) hasta encontrar la persona.
      * iniciarRegistro: valida datos, busca en padrón, genera código y envía
        el email.
      * crearUsuario: delega en servicio-usuarios (/usuarios/registro).
      * sincronizarUsuarioAlumno / sincronizarUsuarioProfesor: hacen PATCH al
        servicio-academico para vincular id_usuario con el alumno/profesor.
      * modificarUsuario: PATCH a servicio-usuarios.
  - codigoDeVerificacion-controller.js:
      * crearCodigoVerificacion: número aleatorio de 6 dígitos.
      * guardarCodigoVerificacion: inserta en tabla codigos_verificacion.
      * verificarCodigoVerificacion: valida que exista, no esté usado y no
        haya expirado; devuelve id_entidad y rol_asociado.
      * invalidarCodigoVerificacion: marca el código como usado.
      * eliminarCodigoVerificacion: borra por id.
  - utils/sendMail.js: usa nodemailer con Gmail (EMAIL_USER / EMAIL_PASS).
    Envía un correo con el código de verificación.

Modelo: codigos_verificacion (ver sección 5, tabla 22).

Detalle del registro (flujo completo):
  1. Frontend envía {dni, nacimiento, email} a /iniciar-registro.
  2. servicio-auth busca la persona en el padrón (alumno o profesor).
  3. Genera código, lo guarda con id_entidad y rol_asociado, envía email.
  4. Frontend envía {nombre, apellido, email, codigo, contrasena} a
     /verificar-codigo.
  5. Se valida el código; se asigna id_rol automáticamente según el
     rol_asociado (alumno→1, profesor→3, administrativo→7) si no se envía.
  6. Se crea el usuario, se sincroniza con el padrón y se emite el token.

 8. FLUJOS PRINCIPALES DE NEGOCIO
================================================================================

A) LOGIN
   1. POST /api/auth/login {email, contrasena}
   2. Gateway reenvía a servicio-auth → servicio-usuarios /usuarios/login.
   3. servicio-usuarios valida email+contraseña (texto plano) y devuelve
      datos + permisos del rol.
   4. servicio-auth genera JWT (8h) y lo devuelve con el usuario.
   5. El frontend guarda el token y lo envía como "Authorization: Bearer ...".
   6. El gateway verifica el token en cada petición protegida.

B) REGISTRO (alumnos y profesores)
   1. POST /api/auth/iniciar-registro {dni, nacimiento, email}
   2. servicio-auth busca en el padrón (alumnos/profesores).
   3. Genera y envía código de 6 dígitos por email (vigencia 15 min).
   4. POST /api/auth/verificar-codigo {nombre, apellido, email, codigo,
      contrasena}
   5. Valida código → crea usuario → vincula con alumno/profesor → token.

C) GESTIÓN ACADÉMICA
   - Administrativos crean cursos, materias, profesores y asignan
     (asignaciones curso-materia-profesor).
   - Profesores cargan notas (0–10) y asistencias (individuales o en lote).
   - Alumnos consultan su curso, compañeros y asignaciones.
   - Las bajas de alumnos/profesores/personal usan soft delete (estado='baja')
     para no perder historial (asistencias, notas).

D) COMUNICADOS
   - Se crean con destino (todos/profesores/alumnos/autoridades/curso).
   - Cada rol recibe solo los comunicados que le corresponden (filtro por
     rol y curso en el controlador).

================================================================================
 11. OBSERVACIONES, BUGS DETECTADOS Y RECOMENDACIONES
================================================================================

Bugs / problemas detectados en el análisis:

  1) Contraseñas en texto plano (servicio-usuarios): se guardan y comparan
     sin hash. bcryptjs está instalado pero no se usa. RIESGO DE SEGURIDAD
     ALTO — se recomienda hashear con bcrypt.

  2) docker-compose.yml eliminado: ahora existe docker-compose.txt. Hay que
     renombrarlo para poder levantar el entorno con docker compose.

  3) CORS hardcodeado en el gateway: solo permite http://186.0.171.84:7070.
     Si el frontend cambia de IP/puerto, hay que editar gateway.js.

  4) Inconsistencia de roles:
     - En la BD root = id_rol 8, pero comprobarPermisos.js de
       servicio-comunidad da bypass a id_rol === 9.
     - En verificar-codigo, rol_asociado 'administrativo' → id_rol 7 (no 9).

  5) servicio-biblioteca tiene múltiples errores de código (ver sección 7.5):
     modelos/imports incorrectos en prestamos- y recursos-controller, update
     con where equivocado, obtenerBiblioteca sin retorno.

  6) cargos-router.js: varias rutas sin la "/" inicial ("cargos/:id",
     "cargos/:id" en patch/delete) y referencia a una variable 'put'
     inexistente en PATCH /cargos/:id.

  7) middleware comprobarPermisos (servicio-academico): hace una llamada HTTP
     a servicio-usuarios en CADA request protegido. Con tráfico alto puede
     convertirse en cuello de botella. Alternativa: incluir los permisos en
     el JWT (como ya hace servicio-comunidad con req.user.permisos).

  8) La tabla sanciones y la tabla tutores_alumnos existen en la BD pero NO
     tienen modelos/controladores en el código (funcionalidad pendiente para
     preceptor y tutor).

  9) Autenticación interna asimétrica: servicio-usuarios y servicio-
     biblioteca no verifican tokens internamente (confían en el gateway);
     servicio-comunidad sí los verifica. Como la red Docker es privada, es
     aceptable, pero cualquier contenedor comprometido podría acceder.

  10) En asistencias, la BD usa el estado 'tardanza' pero el modelo Sequelize
      define el ENUM como 'tarde'. Puede provocar errores de validación al
      usar el estado 'tardanza'.

  11) servicio-comunidad: las rutas POST/PATCH/DELETE usan comprobarPermisos()
      sin permisos concretos, por lo que CUALQUIER usuario autenticado puede
      crear/editar/eliminar noticias, comunicados y objetos perdidos.

  12) prefijos de rutas de biblioteca (/apiBiblioteca, /apiPrestamos,
      /apiRecursos) no coinciden con el prefijo del gateway (/api/biblioteca),
      lo que puede confundir al frontend.

Recomendaciones generales:
  - Implementar hashing de contraseñas (bcrypt) y migrar las existentes.
  - Unificar el manejo de permisos (JWT con permisos o servicio de permisos).
  - Corregir los controladores de biblioteca y las rutas de cargos.
  - Agregar middleware de error global en todos los servicios (solo
    servicio-comunidad lo tiene).
  - Documentar el API con Swagger/OpenAPI para facilitar el consumo del
    frontend.
  - Agregar validación de datos en el body de todas las rutas (DTOs).
